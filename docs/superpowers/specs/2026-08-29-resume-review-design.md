# 简历审阅系统设计文档

日期：2026-08-29
状态：已确认

## 1. 背景与目标

用户（HR/招聘负责人）提供一个岗位 JD 与多份候选人简历（单次 ≤10 份），系统利用私有大模型模拟真人 HR 团队的分工方式，自动完成简历筛选与评价。

**核心输出**：
- 匹配度评分与排序（A/B/C 分档 + 四维评分）
- 逐份评价报告（亮点、风险点、与 JD 差距）
- 结构化信息提取（教育、工作经历、技能、证书等）
- 面试建议问题（每位候选人 3-5 个）

**关键约束**：
- 私有化部署大模型（数据不出内网），通过 OpenAI 兼容接口接入（vLLM/Ollama 部署 Qwen/GLM 等）
- 支持 PDF / Word (docx) / 图片扫描件 / 纯文本粘贴四种简历来源
- PostgreSQL 存储，Docker Compose 一键启动
- 技术栈：Python + FastAPI 后端，Vue3 前端

## 2. 总体架构

```
┌─────────────┐     ┌──────────────────────┐     ┌─────────────┐
│  Web 前端    │────▶│  FastAPI (api 服务)   │────▶│ PostgreSQL   │
│  Vue3+Vite  │ SSE │  - REST API          │     │  (db 服务)   │
│  nginx 托管  │◀────│  - 多角色流水线        │     └─────────────┘
└─────────────┘     │  - 简历解析器          │
                    └──────────┬───────────┘     ┌─────────────┐
                               └────────────────▶│ 私有大模型    │
                                 OpenAI 兼容接口  │ (外部服务，   │
                                                │  配置接入)    │
                                                └─────────────┘
```

### 2.1 Docker Compose 服务清单

| 服务 | 镜像/构建 | 说明 |
|---|---|---|
| `api` | 本地 Dockerfile（Python 3.11 + FastAPI） | REST API、多角色流水线、简历解析 |
| `web` | nginx:alpine | 托管前端构建产物，反向代理 `/api` 到 api 服务 |
| `db` | postgres:16 | 数据卷 `pgdata` 持久化 |
| `ocr`（可选） | PaddleOCR 服务 | 图片/扫描件文字识别，按需启停 |

私有大模型不进 compose，通过环境变量配置：
- `LLM_BASE_URL`（如 `http://内网vLLM地址/v1`）
- `LLM_API_KEY`（私有部署可为占位值）
- `LLM_MODEL`（主模型名，用于各角色推理与文本校正）
- `LLM_VLM_MODEL`（多模态模型名，用于图片 OCR 兜底，如 Qwen-VL / GLM-4V；不配置则禁用兜底通道，OCR 不合格直接标记 `needs_review`）
- `OCR_CONFIDENCE_THRESHOLD`（OCR 合格置信度阈值，默认 0.85）

启动方式：`docker compose up -d` 一键启动全部服务。

## 3. 多角色流水线（核心设计）

模拟真实 HR 团队分工，所有角色共用同一个 OpenAI 兼容客户端，角色差异仅体现在提示词模板（独立存放于 `prompts/` 目录，可随时调整无需改代码）。

| 顺序 | 角色 | 输入 | 输出 |
|---|---|---|---|
| 1 | JD 解析官 | JD 原文 | 结构化 JD：职责、硬性要求（学历/工作年限/必备技能/证书）、加分项、各项权重 |
| 2 | 结构化提取员 | 简历纯文本 | JSON 档案：教育经历、工作经历、技能清单、项目经历、证书 |
| 3 | 初筛专员 | 结构化 JD + 简历档案 | 硬性条件逐条核对，判定「通过/淘汰」+ 逐条理由；淘汰者止步于此，不再进入深度评估 |
| 4 | 资深面试官 | 通过初筛者的档案 + JD | 四维评分（技能匹配/经验匹配/稳定性/潜力，各 0-100）、亮点、风险点、与 JD 差距、3-5 个面试建议问题 |
| 5 | HR 主管 | 全部通过者的评估结果 | 统一排序、A/B/C 分档、最终总结报告 |

### 3.1 编排逻辑

1. 任务创建后，JD 解析官先执行一次，产出结构化 JD 入库。
2. 简历解析器（非 LLM）将各简历文件转为纯文本。
3. 各简历以 `asyncio.Semaphore(3)` 限流并行推进：结构化提取 → 初筛 →（通过者）面试官评估。
4. 全部简历完成后，HR 主管一次性汇总排序，产出最终报告。
5. 每个步骤结果即时写入 PostgreSQL，进度通过 SSE 推送到前端（例：`简历 3/8：资深面试官评估中`）。

### 3.2 简历解析策略（非 LLM 部分）

| 来源 | 解析方式 |
|---|---|
| PDF | PyMuPDF 提取文本；加密/损坏则报失败原因 |
| docx | python-docx 提取文本 |
| 图片/扫描件 | OCR 双通道识别（见 3.3） |
| 纯文本粘贴 | 直接使用 |

补充：PDF 若为扫描版（提取文本量过少，如全文不足 200 字符），自动转入图片通道走 3.3 的 OCR 双通道识别。

### 3.3 图片识别：OCR 主通道 + 多模态 LLM 兜底（双通道）

图片/扫描件简历采用「主通道 + 兜底通道」双通道设计，最大化内容识别准确度：

**通道 1 — PaddleOCR 主通道（默认，成本近零）**
- ocr 服务对图片逐张识别，产出文本及每行平均置信度。
- 质量判定：平均置信度 ≥ 阈值（默认 0.85，环境变量 `OCR_CONFIDENCE_THRESHOLD` 可调）且有效文本量充足 → 视为合格，进入校正步骤。

**通道 2 — 多模态 LLM 兜底**
触发条件（满足其一即触发）：
- PaddleOCR 调用失败或服务不可用；
- 平均置信度低于阈值；
- 识别结果疑似乱码（如非中英文字符占比 > 30%）。

执行方式：将原始图片直接发给私有化部署的多模态模型（环境变量 `LLM_VLM_MODEL` 指定，如 Qwen-VL / GLM-4V，与主模型同一 OpenAI 兼容网关），提示词要求按版面完整转录文字，输出结构化文本。

**共用校正步骤 — LLM 文本校正**
无论哪个通道产出的文本，均追加一次轻量 LLM 校正：提示词要求「修复明显的 OCR 识别错误（形近字、断行、乱码），不改写、不增删任何事实内容」，并将校正前后文本一并入库（`raw_text` 存校正后文本，解析元数据中保留原始文本与所用通道，便于追溯）。

**设计取舍**：多模态模型调用成本高于 PaddleOCR，因此只在 OCR 质量不达标时兜底触发；LLM 校正为无条件轻量步骤（几百 token），换取消化环节的输入质量。

## 4. 数据模型（PostgreSQL）

```
tasks        id (PK), jd_raw (TEXT), jd_parsed (JSONB), status,
             summary_report (JSONB), created_at, updated_at
resumes      id (PK), task_id (FK→tasks), filename, source_type,
             raw_text (TEXT), parse_meta (JSONB), profile (JSONB),
             screening (JSONB), evaluation (JSONB), final_grade (CHAR),
             final_rank (INT), status, error_message, created_at, updated_at
llm_logs     id (PK), task_id (FK), role, prompt_tokens,
             completion_tokens, duration_ms, created_at
```

说明：
- 评估结果全部使用 JSONB 存储，提示词迭代后字段可平滑演化，避免频繁改表结构。
- `status` 枚举：`pending / parsing / extracting / screening / evaluating / done / failed / needs_review`。
- `llm_logs` 记录每次调用的 token 消耗与耗时（role 含各流水线角色、`ocr_fallback`、`text_correct`），用于成本观测与提示词回归分析。
- `parse_meta` 记录解析过程元数据：实际使用的识别通道（`pymupdf / paddleocr / vlm_fallback`）、OCR 置信度、校正前原始文本，便于追溯识别质量问题。

## 5. API 设计

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/tasks` | 创建任务（multipart：JD 文件或文本 + 简历文件列表 + 粘贴文本），校验模型可用性后后台启动流水线 |
| GET | `/api/tasks/{id}` | 任务详情与整体排名、分档结果 |
| GET | `/api/tasks/{id}/events` | SSE 进度流 |
| GET | `/api/resumes/{id}/report` | 单人完整报告（结构化档案 + 评价 + 面试问题） |
| GET | `/api/tasks/{id}/export` | 导出 Markdown / Excel 汇总报告 |
| GET | `/api/health` | 健康检查（含模型连通性预检） |

## 6. 前端页面（Vue3 + Vite + Element Plus）

1. **任务创建页**：JD 上传/粘贴，简历拖拽上传 + 文本粘贴框，文件列表可预删；提交后跳转进度页。
2. **进度页**：流水线可视化——每个候选人一行，节点显示当前所处角色（解析 → 提取 → 初筛 → 面评 → 汇总），SSE 实时刷新。
3. **结果页**：左侧排名榜单（A/B/C 分档色标），点开单人详情：结构化信息表、四维评分雷达图、评价（亮点/风险/差距）、面试建议问题；顶部提供导出入口。

## 7. 错误处理

| 场景 | 处理策略 |
|---|---|
| LLM JSON 输出格式错误 | pydantic 校验失败后自动重试 2 次（重试时附上格式错误说明）；仍失败则该简历标记 `needs_review`，不中断任务 |
| PDF 加密/损坏 | 标记该简历 `failed` 并记录失败原因，不阻塞其他简历 |
| 图片识别：OCR 失败/低置信度/疑似乱码 | 自动触发多模态 LLM 兜底通道重识别；两通道均失败才标记 `failed` |
| 多模态模型不可用（兜底通道失效） | 回退使用 OCR 原始文本并标记 `needs_review`，提示人工核对识别质量 |
| 模型服务不可用 | 任务启动前调用模型连通性预检，失败直接拒绝创建任务并提示 |
| 单简历处理超时 | 设置单步超时（默认 120s），超时按 `needs_review` 处理 |
| 服务重启 | 任务状态落库，重启后 `status` 非终态的任务标记为 `failed` 并提示用户重新发起 |

## 8. 测试策略

- **流水线编排**：pytest + mock LLM 客户端，覆盖状态流转、并发限流、失败重试、淘汰短路等逻辑。
- **简历解析器**：各格式各准备一份样例文件做单元测试（含损坏文件用例）；OCR 双通道单独测试：清晰扫描件（走主通道）、低质量图片（触发兜底）、乱码图（触发兜底）、双通道全失败（标记 failed）。
- **识别质量评估**：用同一批标注样例图片，对比「仅 OCR」与「OCR+LLM 兜底」两条链路的结构化提取字段准确率，作为准确度验收依据。
- **提示词回归**：用固定样例 JD + 样例简历集，对比提示词修改前后的评分与提取结果。
- **端到端**：docker compose 启动全栈后，用样例数据跑通「创建任务 → 进度 → 结果 → 导出」全流程。

## 9. 范围外（YAGNI）

- 不做用户账号体系与多租户（单团队内部使用）
- 不做千份级大规模任务队列（现有 asyncio 并发足够，后续可平移到 Celery）
- 不做在线简历编辑或简历库长期沉淀
- 不做移动端适配
